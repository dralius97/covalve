# ADR-009: Domain Routing via Graph

## Status

Proposed (Revised v3)

---

## Context

In a multi-domain chatbot system, multiple tools can share the same intent, capability, and priority while belonging to different sources of truth.

Example:
- `db_kos_l` → male dormitory (kos putra)
- `db_kos_p` → female dormitory (kos putri)

Both expose tools such as `lookup_room`, `count_available_rooms`, and `lookup_price`. When tool selection operates on a global registry without domain scoping, the following problems arise:

- Tools from multiple domains are invoked simultaneously
- Latency increases
- Results are ambiguous and difficult to trace
- LLM reasoning becomes noisy

This problem is not merely "which tool is most relevant" — it is **"which authority domain does this query belong to."** A domain represents data ownership, policy, authority boundary, and source of truth.

Routing based solely on embedding similarity is insufficient because it does not understand logical relations between domains. Example:

```
"selain di kos putra ada berapa kamar?"
("other than kos putra, how many rooms are available?")
```

Embedding-wise, this query is very close to `kos_putra` — yet the actual intent is `NOT(kos_putra)`, which should resolve to `kos_putri`. This is the tyranny of majority in a scoring system: the loudest signal dominates even when the most authoritative signal should be determinant.

Furthermore, when the system has more than two domains — for example adding a mixed dormitory (`kos_campur`) — a graph-only hard filter is not sufficient. After eliminating `kos_putra`, two candidates remain: `kos_putri` and `kos_campur`. Without an additional reduction step, the resolver must immediately declare ambiguity and fall back to clarification, even when further signal exists to narrow the search space.

A separate and distinct case is the **genuine multi-domain query** — e.g. `"berapa beda harga kos putra dan putri dengan kamar yang sama?"`. Here, two domains are positively (not negated) referenced in a single intent, and the correct resolution is **both domains simultaneously**, not a single winner. This must not be treated as ambiguity to be pruned down to one candidate; collapsing it to one domain silently produces a wrong, half-complete answer instead of a comparison. See "Multi-Domain Output for Comparison Queries" below.

A single-domain deployment (e.g. a system that only ever declares one domain) is not a special case of this design — it is simply a graph where `len(declared_domains) == 1`. The same authority filter and out-of-domain semantics apply unchanged: any query that does not resolve to the one declared domain is `out_of_domain`.

**Scope boundary clarification:** this ADR governs **which authority domain (or domains) a query belongs to** — a question of data ownership and source-of-truth routing. It does not govern:
- whether a query, once routed to a domain, actually requires a tool call versus being answerable from the LLM's own knowledge (a separate concern of temporal/knowledge-freshness, not authority routing).
- which specific tool should be invoked once a domain is known (a separate concern of tool selection, owned by `TOOLS_MAPPER` and the `domain`-scoped tool registry, not by this resolver).

Conflating any of these would expand this resolver beyond its intended responsibility.

## Decision

### 1. Graph as primary routing mechanism

Domain relations are represented as a directed graph with typed edges. This is not a universal knowledge graph — it is a **domain relation graph** representing ownership, relations, authority, hierarchy, exclusion, and alias mappings.

The graph is declared by the system designer, not auto-discovered by AI, because domain relationships are deterministic and business-defined.

Example declaration:

```python
GRAPH = {
    "kos_putra": {
        "aliases": ["putra", "cowok", "ikhwan"],
        "excludes": ["kos_putri"],
    },
    "kos_putri": {
        "aliases": ["putri", "cewek", "akhwat"],
        "excludes": ["kos_putra"],
    },
    "melati": {
        "belongs_to": "kos_putri"
    }
}
```

### 2. Two-layer resolution, plus last-resort pruning

The graph acts as a **hard constraint**, not as a voter in a weighted scoring system. The mechanism is separated as follows:

```
Layer 1 — Authority Filter (graph):
  Eliminate domains based on logical relations (excludes, belongs_to).
  Consumes ANALYZE's entities/filters — negation (FilterOperator.NEQ /
  NOT_IN) on a domain-aliased entity triggers elimination via the
  declared `excludes` relation. Non-negotiable. Occurs before any
  scoring.
  Positively-referenced, non-conflicting domains are NOT collapsed
  here — see "Multi-Domain Output" below.

Layer 2 — Alias Resolution (mode-dependent):
  graph mode  (default): no additional signal beyond Layer 1's alias
              map. If 2+ candidates remain, they pass through
              unchanged to Pruning.
  corpus mode (opt-in):  delegates to a `CorpusBase` plugin (embedding
              similarity), scored ONLY among the candidates that
              survived Layer 1 — not the full domain set. This is
              where unanticipated synonyms get resolved.

Pruning — Last Resort:
  Applied only if Layer 1 + Layer 2 still leave 2+ candidates, as a
  final attempt before declaring ambiguous/out_of_domain. Uses
  session history and recency/explicitness only (capability check is
  explicitly NOT part of this resolver — see section 8). If pruning
  still leaves 2+ candidates, the resolver declares `ambiguous` and
  transitions to FALLBACK.
```

With this separation, `exclude(kos_putra)` immediately eliminates `kos_putra` from candidates before any further processing — regardless of its embedding score.

**Design rationale for ordering (corpus before pruning):** corpus mode and pruning resolve different *kinds* of ambiguity. Corpus resolves **semantic** ambiguity (unanticipated synonyms/phrasing); pruning resolves **pragmatic** ambiguity (conversational context — what was recently discussed). An implementor who opts into corpus mode is explicitly asking for stronger semantic resolution; it is reasonable for that mechanism to run first, with pruning as the final, cheaper fallback for cases where even semantic matching cannot differentiate. **Trade-off accepted:** this ordering does not minimize cost — in corpus mode, embedding inference runs on every query where Layer 1 leaves 2+ candidates, even in cases pruning alone could have resolved more cheaply. This is an explicit choice, not an oversight.

### 3. Multi-Domain Output for Comparison Queries

When a query positively references multiple domains that do not exclude one another (e.g. a comparison intent), Layer 1 must output **all matching domains**, not a single winner pruned down by Layer 2/Pruning.

- `ContentUnit.domain` is typed as `list[str]`, not `Optional[str]`. A single-domain resolution is simply a list of length 1.
- Layer 2 and Pruning are **bypassed entirely** when Layer 1 resolves to multiple non-conflicting, positively-referenced domains — this is not an ambiguity state, no further disambiguation should be attempted.
- Downstream, the Scoped Tool Registry and `TOOLS_MAPPER`/`EXECUTE_TOOLS` must support resolving and executing tools across multiple domains in parallel (the same `asyncio.gather` pattern used elsewhere in the runtime), with `MAIN_LLM` responsible for synthesizing the combined result.
- This ADR does not yet specify the precise mechanism `ANALYZE` uses to flag an intent as "multi-target" (e.g. `intent: "compare"`) versus genuinely ambiguous; that distinction is assumed to already exist in `ContentUnit.intent` and is out of scope for this resolver to redefine.

### 4. Pre-compiled hash table for O(1) lookup

The graph declared at startup is compiled into pre-computed lookup tables:

```python
COMPILED = {
    "alias_map": {
        "putra": "kos_putra",
        "cowok": "kos_putra",
        "putri": "kos_putri",
        "cewek": "kos_putri",
    },
    "exclude_map": {
        "kos_putra": ["kos_putri"],
        "kos_putri": ["kos_putra"]
    },
    "domain_map": {
        "melati": "kos_putri"
    }
}
```

Alias resolution happens inside the graph — not in a separate layer. Multi-hop traversal is pre-computed at initialization so all lookups become O(1) at runtime. The graph is static — no dynamic domain registration occurs at runtime.

### 5. Context Stack as complementary layer

The Context Stack handles conversational carry-over — not as a primary routing mechanism, but as a fallback when a query contains no explicit entity.

```
explicit entity present?
  YES → graph traversal directly
  NO  → check context stack
         active domain exists?
           YES → use as starting point for graph traversal
           NO  → ambiguous → FALLBACK
```

### 6. Ambiguity and out-of-domain as explicit states

The resolver distinguishes two failure conditions:

- **Ambiguous** — Layer 1, Layer 2, and last-resort Pruning collectively yield more than one candidate with no remaining signal to differentiate, or context stack is empty with no explicit entity. Resolver sets `fallback_reason: "ambiguous"` and transitions to FALLBACK. The LLM in FALLBACK formulates a clarification request to the user.

- **Out-of-domain** — graph traversal yields no valid candidate. This applies identically whether the system declares one domain or many. Resolver sets `fallback_reason: "out_of_domain"` and transitions to FALLBACK. The LLM in FALLBACK formulates a scope boundary response.

Both conditions are routed to the existing FALLBACK node, with `fallback_reason` in the context payload as a signal for the LLM.

### 7. Dual-Mode Scoring and Corpus Mode Notice

Mode is selected via config, not hardcoded:

```python
DOMAIN_ROUTER_CONFIG = {
    "mode": "graph",          # or "corpus"
    "graph": GRAPH,
    "corpus_plugin": None,    # required when mode="corpus"
}
```

**`mode: "graph"` (default)** — pure dict + pre-compiled hash table lookup. Zero new external dependency, consistent with covalve's core zero-dependency principle. Relies entirely on explicitly declared aliases.

**`mode: "corpus"` (opt-in)** — delegates Layer 2 resolution to a `CorpusBase` plugin (e.g. `covalve-corpus`, backed by sentence embeddings).

> **Notice (must be surfaced to implementors, not buried in docs):** enabling corpus mode delegates alias resolution to ML-based embedding similarity. This introduces (a) additional inference latency on every query where Layer 1 leaves 2+ candidates, and (b) semantic-match behavior instead of exact declared-alias behavior, which can feel less predictable than graph mode. covalve should emit a runtime warning at `DOMAIN_ROUTER` initialization when `mode == "corpus"` is configured, analogous to other environment-consequence warnings already surfaced elsewhere in the stack (e.g. unauthenticated Hugging Face Hub requests), so the trade-off is visible at startup rather than discovered later through latency or behavior surprises.

The choice between modes is the implementor's, made explicit through configuration. covalve does not default to `corpus` mode silently.

### 8. Tool Scoping Is Independent of Domain Resolution

`DOMAIN_ROUTER` never consumes information about which tool a query implies, and never uses tool capability as a signal for domain disambiguation. This was previously proposed as a "capability check" pruning signal and is now explicitly excluded from this resolver's responsibility, for two reasons:

- **Ordering:** tool selection (`TOOLS_MAPPER`) occurs *after* `DOMAIN_ROUTER` in the runtime flow. A capability-based signal would require knowing which tool is implied before tool mapping has run — an unresolved circular dependency.
- **Scope purity:** using tool capability to infer domain re-conflates authority routing with tool necessity, which section "Scope boundary clarification" above explicitly rules out.

Tool-to-domain scoping is handled entirely downstream, by the **Scoped Tool Registry**, which filters the tool registry using the `domain` key already required on every tool declaration (see Consequences). `DOMAIN_ROUTER` produces a domain (or list of domains); the Scoped Tool Registry consumes it to restrict which tools `TOOLS_MAPPER` may even consider. No information flows the other direction.

**Trade-off accepted:** without capability as a disambiguation signal, queries that previously could have been resolved by "only domain X exposes the implied tool" will, if Layer 2/Pruning also cannot differentiate, fall through to `ambiguous` and request clarification more often than a capability-aware design would. This is accepted as the cost of keeping domain authority and tool selection as cleanly separated concerns.

### 9. Dependency posture

Core graph-mode implementation uses Python dict and pre-compiled hash tables only. No new dependency is introduced in covalve core. Corpus-mode is strictly opt-in via plugin and does not affect implementors who do not enable it. This preserves covalve's zero-dependency principle at the core while allowing probabilistic scoring as an explicit, isolated, and clearly-notified extension.

## Consequences

### Required changes

**ANALYZE node** — already satisfies this requirement under different naming. The structured semantic output called for by this ADR is already implemented as `ContentUnit.entities: list[EntityUnit]` and `ContentUnit.filters: list[FilterUnit]` (where negation/exclusion is expressed via `FilterOperator.NEQ` / `NOT_IN`). No further change to ANALYZE is required for this ADR.

**ContentUnit** — requires a new field to carry the resolver's output, since `DOMAIN_ROUTER` is a native node operating with full read/write access to `PipelineContext` (unlike custom nodes, which only receive scoped, partially read-only context):

```python
class ContentUnit(BaseModel):
    intent: str
    composition_context: str
    confidence: float
    metric: Optional[Metric] = None
    entities: list[EntityUnit] = []
    filters: list[FilterUnit] = []
    domain: list[str] = []   # populated by DOMAIN_ROUTER; [] = unresolved/out_of_domain
```

**FALLBACK node** — must handle `fallback_reason` from context payload to differentiate response behavior between ambiguous queries and out-of-domain queries.

**tools_schema** — requires a new `domain` key on every tool declaration:

```python
Tool(
    name="query_room_putra",
    domain="kos_putra",
    datasource="db_kos_l"
)
```

The Scoped Tool Registry derives a scoped tool set from `ContentUnit.domain` (now a list) matched against the `domain` key in tools metadata. Only tools whose domain matches one of the resolved domains are forwarded to `TOOLS_MAPPER`. The exact consuming mechanism is intentionally left as an implementation detail.

### New layer in runtime flow

```
query
→ ANALYZE (semantic extraction)
→ DOMAIN_ROUTER (native node)
    ├── Layer 1: Authority Filter (graph traversal, multi-domain aware)
    ├── Layer 2: Alias Resolution (no-op in graph mode / corpus scoring in corpus mode)
    └── Pruning: last resort (session history + recency only)
→ Scoped Tool Registry (filters tools by `domain` key — independent of DOMAIN_ROUTER)
→ TOOLS_MAPPER
→ EXECUTE_TOOLS (parallel across domains when ContentUnit.domain has length > 1)
```

`DOMAIN_ROUTER` is a native node, not a custom node — it requires full read/write access to `PipelineContext.metadata` to annotate `ContentUnit.domain` in place.

### Trade-offs

**Advantages**

- **Handles multi-domain edge cases gracefully** — last-resort pruning still reduces candidates before declaring ambiguity, when more than two domains exist and the hard filter alone is insufficient.
- **Handles genuine multi-domain (comparison) queries correctly** — these are no longer silently collapsed to one domain.
- **Deterministic and explainable by default** — graph-mode routing decisions can be traced back to explicit graph relations.
- **Handles logical relations natively** — negation, exclusion, ownership, and hierarchy are first-class concepts.
- **No mandatory training data or dependency** — graph mode encodes business rules directly.
- **O(1) runtime performance in graph mode.**
- **Clean separation of concerns** — domain authority, tool necessity, and tool selection are three distinct, non-conflated responsibilities.
- **Corpus mode's cost/behavior trade-off is explicit and surfaced**, not discovered later.

**Disadvantages**

- **Graph maintenance is manual** — domain relations that are not declared will not resolve.
- **Static by design** — the compiled table must be rebuilt if graph declarations change.
- **Alias coverage is bounded in graph mode** — unexpected synonyms outside the declared alias map will not resolve unless corpus mode is enabled.
- **Corpus mode runs more often than strictly necessary** — by design, it is tried before pruning, so it does not benefit from cheap-signal short-circuiting. Cost-sensitive implementors should be aware of this.
- **Loss of capability-based disambiguation** — queries previously resolvable via "which domain exposes the implied tool" now fall through to ambiguous/clarification more often, since `DOMAIN_ROUTER` no longer uses tool capability as a signal.
- **Context Stack staleness** — conversational carry-over can produce incorrect routing if the active domain is not reset on intent shift.
- **Does not address tool-necessity within a domain** — whether a resolved query still requires a tool call is explicitly out of scope.

## Alternatives Considered

| Approach | Reason Rejected |
|---|---|
| Pure embedding similarity | Weak against negation and logical relations |
| LLM-based routing | Non-deterministic, not explainable, no separation of concern |
| Pure rule-based | Brittle, not scalable, negation difficult to handle cleanly |
| SetFit / XGBoost classifier | Requires training data, introduces new dependencies, negation problem remains |
| FSM-only | State explosion for multi-domain systems, inter-domain relations are unnatural to express as states |
| NetworkX | New dependency not justified for a static and relatively small graph |
| Single mandatory embedding-based Layer | Forces a dependency on all implementors regardless of need; rejected in favor of opt-in corpus mode |
| Folding tool-necessity decision into DOMAIN_ROUTER | Conflates authority routing with knowledge-freshness, expanding the resolver beyond a single, well-defined responsibility |
| Capability check as a domain-disambiguation signal | Requires tool-implied-ness to be known before `TOOLS_MAPPER` runs (circular dependency), and re-conflates domain authority with tool selection |
| Pruning before mode-dependent scoring (cost-first ordering) | Optimizes for inference cost over resolution accuracy; rejected in favor of resolving semantic ambiguity (corpus) before pragmatic ambiguity (pruning), as an explicit, documented trade-off |
