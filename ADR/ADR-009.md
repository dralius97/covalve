# ADR-009: Domain Routing via Graph

## Status

Proposed

---

## Context

In a multi-domain chatbot system, multiple tools can share the same intent, capability, and priority while belonging to different sources of truth.

Example:
- `db_kos_l` → male dormitory (kos putra)
- `db_kos_p` → female dormitory (kos putri)

Both expose tools such as `lookup_room`, `count_available_rooms`, and `lookup_price`. When tool selection operates on a global registry without domain scoping, the following problems arise:

- Tools from multiple domains are invoked simultaneously
- Latency increases
- Results are ambiguous and difficult to trace
- LLM reasoning becomes noisy

This problem is not merely "which tool is most relevant" — it is **"which authority domain does this query belong to."** A domain represents data ownership, policy, authority boundary, and source of truth.

Routing based solely on embedding similarity is insufficient because it does not understand logical relations between domains. Example:

```
"selain di kos putra ada berapa kamar?"
("other than kos putra, how many rooms are available?")
```

Embedding-wise, this query is very close to `kos_putra` — yet the actual intent is `NOT(kos_putra)`, which should resolve to `kos_putri`. This is the tyranny of majority in a scoring system: the loudest signal dominates even when the most authoritative signal should be determinant.

Furthermore, when the system has more than two domains — for example adding a mixed dormitory (`kos_campur`) — a graph-only hard filter is not sufficient. After eliminating `kos_putra`, two candidates remain: `kos_putri` and `kos_campur`. Without an additional reduction step, the resolver must immediately declare ambiguity and fall back to clarification, even when further signal exists to narrow the search space.

---

## Decision

### 1. Graph as primary routing mechanism

Domain relations are represented as a directed graph with typed edges. This is not a universal knowledge graph — it is a **domain relation graph** representing ownership, relations, authority, hierarchy, exclusion, and alias mappings.

The graph is declared by the system designer, not auto-discovered by AI, because domain relationships are deterministic and business-defined.

Example declaration:

```python
GRAPH = {
    "kos_putra": {
        "aliases": ["putra", "cowok", "ikhwan"],
        "excludes": ["kos_putri"],
        "db": "db_kos_l"
    },
    "kos_putri": {
        "aliases": ["putri", "cewek", "akhwat"],
        "excludes": ["kos_putra"],
        "db": "db_kos_p"
    },
    "melati": {
        "belongs_to": "kos_putri"
    }
}
```

### 2. Three-layer resolution: authority filter, pruning, then scoring

The graph acts as a **hard constraint**, not as a voter in a weighted scoring system. The mechanism is separated into three distinct layers:

```
Layer 1 — Authority Filter (graph):
  Eliminate domains based on logical relations.
  Non-negotiable. Occurs before any scoring.

Layer 2 — Search Space Pruning:
  Further reduce candidates using soft signals before scoring.
  Probabilistic, not deterministic.

Layer 3 — Soft Scoring (embedding + lexical + context):
  Tiebreaker among candidates that survive Layer 1 and Layer 2.
```

With this separation, `exclude(kos_putra)` immediately eliminates `kos_putra` from candidates before any further processing — regardless of its embedding score.

**Layer 2 — Search Space Pruning** addresses the multi-domain edge case where Layer 1 still yields more than one candidate. Pruning applies the following signals in order:

- **Capability check** — if the query implies a specific tool (e.g. `count_available_rooms`), candidates that do not expose that tool are pruned. This is O(1) via the scoped tool registry.
- **Session history** — candidates that have never appeared in the current session are de-prioritized. A domain that has never been mentioned is less likely to be the implicit target.
- **Recency and explicitness** — among remaining candidates, those mentioned more recently or more explicitly in session history rank higher.

Pruning does not produce a final decision — it reduces the search space so that Layer 3 scoring or FALLBACK operates on a smaller, more relevant candidate set. If pruning reduces candidates to exactly one, scoring is skipped entirely.

### 3. Pre-compiled hash table for O(1) lookup

The graph declared at startup is compiled into pre-computed lookup tables:

```python
COMPILED = {
    "alias_map": {
        "putra": "kos_putra",
        "cowok": "kos_putra",
        "putri": "kos_putri",
        "cewek": "kos_putri",
    },
    "exclude_map": {
        "kos_putra": ["kos_putri"],
        "kos_putri": ["kos_putra"]
    },
    "domain_map": {
        "melati": "kos_putri"
    }
}
```

Alias resolution happens inside the graph — not in a separate layer. Multi-hop traversal is pre-computed at initialization so all lookups become O(1) at runtime. The graph is static — no dynamic domain registration occurs at runtime.

### 4. Context Stack as complementary layer

The Context Stack handles conversational carry-over — not as a primary routing mechanism, but as a fallback when a query contains no explicit entity.

```
explicit entity present?
  YES → graph traversal directly
  NO  → check context stack
         active domain exists?
           YES → use as starting point for graph traversal
           NO  → ambiguous → FALLBACK
```

### 5. Ambiguity and out-of-domain as explicit states

The resolver distinguishes two failure conditions:

- **Ambiguous** — graph traversal yields more than one candidate with scores too close to differentiate, or context stack is empty with no explicit entity. Resolver sets `fallback_reason: "ambiguous"` and transitions to FALLBACK. The LLM in FALLBACK formulates a clarification request to the user.

- **Out-of-domain** — graph traversal yields no valid candidate. Resolver sets `fallback_reason: "out_of_domain"` and transitions to FALLBACK. The LLM in FALLBACK formulates a scope boundary response.

Both conditions are routed to the existing FALLBACK node, with `fallback_reason` in the context payload as a signal for the LLM.

### 6. Zero new external dependency

Implementation uses Python dict and pre-compiled hash tables. No new dependencies are introduced beyond the existing Pydantic dependency. Consistent with covalve's zero-dependency principle.

## Consequences

### Required changes

**ANALYZE node** — must emit structured semantic output including entities and operators, not just a plain sentence:

```json
{
  "intent": "lookup",
  "composition_context": "selain di kos putra ada berapa kamar",
  "semantic": {
    "entities": [
      { "type": "domain", "value": "kos_putra" }
    ],
    "operators": [
      { "type": "exclude", "target": "kos_putra" }
    ]
  }
}
```

**FALLBACK node** — must handle `fallback_reason` from context payload to differentiate response behavior between ambiguous queries and out-of-domain queries.

**tools_schema** — requires a new `domain` key on every tool declaration:

```python
Tool(
    name="query_room_putra",
    domain="kos_putra",
    datasource="db_kos_l"
)
```

The resolver derives a scoped tool registry from the combination of the active domain produced by graph traversal and the `domain` key in tools metadata. Only tools whose domain matches the active domain are forwarded to the planner.

### New layer in runtime flow

```
query
→ ANALYZE (semantic extraction)
→ Domain Resolver
    ├── Layer 1: Authority Filter (graph traversal)
    ├── Layer 2: Search Space Pruning (capability + session history)
    └── Layer 3: Soft Scoring (tiebreaker)
→ Scoped Tool Registry
→ PLANNER
→ EXECUTOR
```

The Domain Resolver is a new layer between ANALYZE and tool selection. Resolver complexity is entirely internal — implementors only need to declare the graph and assign `domain` on tools. Traversal mechanics are invisible to the implementor.

### Trade-offs

**Advantages**

- **Handles multi-domain edge cases gracefully** — Search Space Pruning reduces candidates before scoring, avoiding premature FALLBACK when more than two domains exist and hard filter alone is insufficient.
- **Deterministic and explainable** — routing decisions can be traced back to explicit graph relations. Debugging is straightforward: if routing is wrong, the graph declaration is wrong.
- **Handles logical relations natively** — negation, exclusion, ownership, and hierarchy are first-class concepts. These cannot be expressed cleanly by embedding similarity alone.
- **Zero training data required** — the graph encodes business rules directly. No labeled dataset is needed.
- **O(1) runtime performance** — pre-compiled hash tables eliminate traversal cost at query time.
- **Clean DX for implementors** — complexity is hidden inside the resolver. Implementors declare domain relations once; routing behavior follows automatically.
- **No new dependencies** — consistent with covalve's existing architecture.

**Disadvantages**

- **Graph maintenance is manual** — domain relations that are not declared will not resolve. As the system grows, graph declarations must be kept in sync with actual domain boundaries.
- **Static by design** — the compiled table must be rebuilt if graph declarations change. This only occurs on new deployments, but dynamic domain registration is not supported.
- **Alias coverage is bounded** — the graph only knows aliases that are explicitly declared. Unexpected synonyms or typos that fall outside the alias map will not resolve correctly without a fuzzy matching layer.
- **Context Stack staleness** — conversational carry-over can produce incorrect routing if the active domain is not reset on intent shift. Lifecycle management for active domain is required as part of resolver implementation.
- **Pruning signal reliability** — Layer 2 pruning relies on session history and capability checks. In early-session queries with no history and ambiguous capability overlap, pruning may not reduce the candidate set meaningfully, and FALLBACK remains the correct outcome.
- **Does not handle cross-domain queries natively** — queries that genuinely require multiple domains simultaneously (e.g. comparison queries) are not covered by this ADR and require separate design.

---

## Alternatives Considered

| Approach | Reason Rejected |
|---|---|
| Pure embedding similarity | Weak against negation and logical relations |
| LLM-based routing | Non-deterministic, not explainable, no separation of concern |
| Pure rule-based | Brittle, not scalable, negation difficult to handle cleanly |
| SetFit / XGBoost classifier | Requires training data, introduces new dependencies, negation problem remains |
| FSM-only | State explosion for multi-domain systems, inter-domain relations are unnatural to express as states |
| NetworkX | New dependency not justified for a static and relatively small graph |
