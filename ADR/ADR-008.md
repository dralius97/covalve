# ADR-008: Pipeline Cancellation via asyncio.Event

## Status
#Proposed

## Date
2026-05-30

## Context
The current engine runs as an uninterruptible async loop. Once a pipeline
execution begins, there is no mechanism to stop it externally — not from
a user action, not from a system condition, and not from a timeout.

In practice, implementors building on top of covalve will face scenarios
where cancellation is necessary:

- A user manually stops a request from the UI before a response is returned
- A system-level condition (rate limit, quota exceeded, upstream failure)
  requires the pipeline to be aborted
- A timeout policy needs to be enforced at the pipeline level

Without a cancellation mechanism, the pipeline will continue executing
through all remaining states regardless of external signals, wasting
compute on LLM calls and tool executions that will never be delivered.

The behavior of major LLM products (ChatGPT, Claude, Grok) when a user
cancels a request is consistent: the response is discarded and not persisted.
This is the expected UX contract.

## Decision

### Cancellation signal
Extend the `engine` function signature to accept an optional
`asyncio.Event` as a cancellation signal:

```python
async def engine(query, session_id=None, cancel_event: asyncio.Event = None):
```

If `cancel_event` is not provided, the engine behaves as before — no
cancellation is possible. This is a non-breaking change.

### Check point
The engine checks `cancel_event.is_set()` at the start of each iteration,
before executing the next state:

```python
while current_state not in stop_state:
    if cancel_event and cancel_event.is_set():
        current_state = STOP.CANCELLED
        break
```

The check happens between state transitions, not mid-executor. An executor
that is already running will complete before the cancellation is observed.
This is intentional — partial executor state is worse than a completed
executor that gets discarded.

### STOP.CANCELLED terminal state
Add `STOP.CANCELLED` to the `STOP` enum and include it in `stop_state`:

```python
class STOP(str, Enum):
    INVALID_EVENT = "INVALID_EVENT"
    HANDLER_ERROR = "HANDLER_ERROR"
    INTERCEPTOR_ERROR = "INTERCEPTOR_ERROR"
    CANCELLED = "CANCELLED"
```

### Discard on cancel
When `STOP.CANCELLED` is reached, the engine exits the loop without
routing to `SAVE_DATA_TO_PERSISTENCE`. The partial context is discarded
and not persisted. This is consistent with the UX contract of major LLM
products.

### Audit trail
Cancellation is recorded via the existing `StateLog` mechanism.
The final log entry will reflect `next_state: CANCELLED`, providing
a full audit trail of which states were executed before cancellation
without requiring a separate logging concern.

### Timeout as a special case
Timeout is not implemented as a separate mechanism. Implementors who need
timeout behavior can wrap the engine call with `asyncio.wait_for`, or
set the `cancel_event` from a timer. Timeout is a cancellation trigger,
not a distinct concept.

## Rationale
`asyncio.Event` is the most natural fit for this pattern in an async Python
runtime — it is lightweight, composable, and implementor-controlled. The
implementor decides when and why to set the event; covalve only observes it.

Checking at iteration boundaries rather than mid-executor preserves executor
atomicity. A partially executed state is harder to reason about than a
cleanly cancelled pipeline.

Discarding on cancel is consistent with user expectations and avoids storing
incomplete or misleading conversation history in persistence.

The existing `StateLog` fire-and-forget mechanism already captures every
state transition — `STOP.CANCELLED` as a terminal state is sufficient for
audit purposes without additional instrumentation.

## Consequences

### Positive
- Non-breaking change — `cancel_event` is optional
- Implementor controls cancellation trigger — UI, timeout, system condition,
  or any external signal
- Executor atomicity preserved — no partial executor state
- Audit trail via existing `StateLog` at zero additional cost
- Timeout is naturally composable without a separate mechanism

### Negative
- Cancellation is only observed between state transitions — a long-running
  executor (e.g. slow LLM call) will not be interrupted mid-execution
- Implementors must manage the `asyncio.Event` lifecycle themselves —
  reuse across requests without reset will cause unexpected cancellations
- Discarding on cancel means no partial conversation history is saved —
  implementors who want partial persistence must handle this themselves
  via hooks or custom executors before the cancel point
