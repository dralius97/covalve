# ADR-010: Custom Node Interface via Higher-Order Function

## Status
#Accepted

## Date
2026-06-09

## Context
covalve provides `add_handlers` and `overrides` in `PipelineConfig` for
implementors to inject custom nodes. However, the current interface requires
implementors to have deep knowledge of covalve internals:

- `ArgsCtx` and `ReturnSchema` structure
- `PipelineContext` field layout and semantics
- `model_copy(update={...})` pattern from ADR-005
- Which native fields are safe to write vs which belong to native node contracts

This coupling creates two problems:

**Problem 1 — High cognitive load.** An implementor building a custom node
must read the source of `PipelineContext`, understand ADR-005, and manually
map their output to the correct field. A mistake — writing to the wrong field,
or mutating directly instead of `model_copy` — silently corrupts pipeline state
with no early warning.

**Problem 2 — No boundary enforcement.** ADR-007 introduced `local` as the
designated space for custom-to-custom communication. But nothing prevents a
custom node from writing to native fields like `metadata` or `tools_data`
without intent. There is no contract that makes the boundary explicit.

The desired state: an implementor declares what data they need, receives a
typed context scoped to exactly that, and returns a typed output. The runtime
handles all `PipelineContext` read/write mechanics invisibly.

## Decision

### 1. NodeContext — scoped context object

`NodeContext` is the context object injected into custom node functions.
Its contents are determined by the `reads` declaration on the decorator.

`readonly` is always present regardless of `reads`. It contains fields
that are runtime-generated and immutable for the duration of execution.

```python
class NodeContext(BaseModel):
    readonly: ReadOnlyFields
    conversation: Optional[ConversationFields] = None
    tools: Optional[ToolsFields] = None
    response: Optional[ResponseFields] = None
    errors: Optional[ErrorFields] = None
    custom: Optional[CustomFields] = None
```

Field categories map directly to `PipelineContext`:

| Category | Fields |
|---|---|
| `readonly` | `query`, `session_id`, `current_time`, `traceId` |
| `conversation` | `background`, `metadata` |
| `tools` | `tools_data`, `executed_tools`, `tool_list` |
| `response` | `response`, `summarize`, `is_clarification`, `fallback_content`, `guardrail_rejection` |
| `errors` | `error`, `last_error_emitted` |
| `custom` | `local` |

If a category is not declared in `reads`, its field on `NodeContext` is `None`.
Accessing an undeclared category returns `None` — implementors are responsible
for only accessing what they declared.

### 2. ReturnContext — typed output

`ReturnContext` is the return type for all custom node functions.
`event` is required. All other fields are optional — only non-`None`
fields are merged back into `PipelineContext`.

```python
class ReturnContext(BaseModel):
    event: str
    local: Optional[dict[str, Any]] = None
    errors: Optional[ErrorFields] = None
    response: Optional[ResponseFields] = None
    tools: Optional[ToolsFields] = None
    conversation: Optional[ConversationFields] = None
```

`writes` is intentionally absent. The HOF infers write targets from
`ReturnContext` at runtime via selective merge — only non-`None` category
fields are written back to `PipelineContext`. This eliminates redundant
declaration while keeping the merge behavior deterministic.

### 3. `@node.handler` decorator

The decorator wraps the implementor's function and produces a factory
compatible with `add_handlers` and `overrides` in `PipelineConfig`.

```python
@node.handler(reads=["conversation", "tools"])
async def my_custom_node(ctx: NodeContext) -> ReturnContext:
    query = ctx.readonly.query
    background = ctx.conversation.background
    return ReturnContext(
        event="NEXT",
        conversation=ConversationFields(metadata=result)
    )
```

`reads` accepts a list of category names: `"conversation"`, `"tools"`,
`"response"`, `"errors"`, `"custom"`. `"readonly"` is implicit and always
injected — it must not be declared in `reads`.

The decorator produces a factory function compatible with the existing
handler registry pattern:

```python
def factory(deps: InfrastructureRegistry):
    async def handle(ctx: ArgsCtx) -> ReturnSchema:
        # 1. build NodeContext from reads declaration
        # 2. call implementor function
        # 3. selective merge ReturnContext into PipelineContext
        # 4. return ReturnSchema(event=..., context=...)
    return handle
```

Implementors who register via `add_handlers` pass the decorated function
directly as the factory — the decorator handles the factory wrapping:

```python
config = PipelineConfig(
    dependencies=deps,
    add_handlers={"MY_CUSTOM_NODE": my_custom_node}
)
```

### 4. Selective merge behavior

The HOF merges `ReturnContext` into `PipelineContext` field by field,
skipping any category that is `None`. Within a non-`None` category,
only non-`None` fields are written — existing `PipelineContext` values
for unset fields are preserved.

```
ReturnContext.conversation = ConversationFields(metadata=result, background=None)
→ PipelineContext.metadata = result       ✓ written
→ PipelineContext.background = unchanged  ✓ preserved
```

Full replace per category is explicitly rejected — it would silently
discard data written by earlier nodes (e.g. `background` populated by
`RETRIEVE_PREVIOUS_CONVERSATION` would be lost if a downstream custom
node returns `ConversationFields` with only `metadata` set).

ADR-005 compliance is maintained — the HOF uses `model_copy(update={...})`
internally. The implementor never touches `PipelineContext` directly.

### 5. `reads` validation at startup

`init_handlers` validates `reads` declarations at startup:

- Unknown category names raise `ValueError`
- `"readonly"` in `reads` raises `ValueError` — it is implicit, not declarable

This catches misconfiguration before the pipeline accepts any request,
consistent with the startup validation pattern established in ADR-003
for hook `on_false` events.

## Rationale

The `reads` declaration as the single source of truth eliminates the
redundancy of declaring both `reads` and function parameters separately.
The implementor declares intent once; the HOF fulfills it.

Nested `NodeContext` (e.g. `ctx.conversation.background`) is more
consistent with `reads` semantics than a flat context — the structure
of the object mirrors the declaration. An implementor who did not declare
`"tools"` in `reads` will find `ctx.tools` is `None`, which is an
immediate and visible signal rather than a subtle data absence.

Inferring writes from `ReturnContext` rather than requiring explicit
declaration reduces surface area without losing determinism. The merge
behavior is fixed and documented — implementors do not need to reason
about it.

The decorator producing a factory-compatible output means zero changes
to the existing handler registry, `init_handlers`, or engine. The HOF
is purely an implementor-facing convenience layer — the runtime internals
remain unchanged.

## Consequences

### Positive
- Implementors never interact with `PipelineContext`, `ArgsCtx`, or
  `ReturnSchema` directly
- ADR-005 compliance is guaranteed by the HOF — mutation is impossible
  from the implementor's perspective
- `reads` declaration makes data dependencies explicit and auditable
- Selective merge preserves existing context state — no accidental overwrites
- Zero changes to engine, registry, or init — purely additive
- Startup validation catches `reads` misconfiguration early

### Negative
- Implementors must learn a new abstraction layer — `NodeContext`,
  `ReturnContext`, and the category system — before writing their first node
- Accessing an undeclared category returns `None` silently — no runtime
  error until the implementor tries to access a field on `None`
- Custom nodes that need fine-grained control (e.g. partial tool_list
  manipulation) may find the category granularity too coarse
- `reads` validation at startup only catches unknown category names —
  it cannot verify that the declared categories will be populated by
  the time the node runs

### Open Question
If `reads=["tools"]` is declared but `tools_data` is `None` at runtime
because `EXECUTE_TOOLS` has not run yet, `ctx.tools.tools_data` will be
`None`. This is a runtime data absence, not a misconfiguration — the HOF
has no way to distinguish these. Documentation must make this explicit:
`reads` declares access intent, not a guarantee of data presence.
