# ADR-003: Plugin System Design

## Status
#Proposed

## Date
2026-05-19

## Context
As the runtime matured, there was a need to accommodate cross-cutting concerns
such as state transition logging, audit trails, and notifications without
coupling these concerns into the executor logic. Executors should remain focused
on their single responsibility — processing a state and returning an event.

Hardcoding observability and extensibility logic directly into executors would
violate separation of concerns and make the runtime harder to maintain and extend.

## Decision
Introduce a plugin system that allows implementors to attach optional behavior
to any node in the pipeline via a `plugins.json` configuration file.

Plugins operate in two modes:

- **Hanging** — fire-and-forget, executed via `asyncio.create_task()`. Used for
  observability concerns such as logging, metrics, and notifications that should
  not block the pipeline.

- **Middleware** — blocking, executed via `await`. Can return a result that
  influences whether the pipeline continues or redirects. Used for concerns
  that need to intercept execution before or after a node runs.

Plugins are configured declaratively:

```json
{
  "ANALYZE": {
    "plugins": [
      {
        "name": "tokenisation",
        "type": "hanging",
        "on": "exit"
      },
      {
        "name": "guardrail",
        "type": "middleware",
        "on": "enter",
        "on_false": "OUT_OF_SCOPE"
      }
    ]
  }
}
```

`on_false` emits an **event**, not a direct node name. The runtime resolves
the event against `schema.json` transitions — identical to how executors work.
This means `on_false` events must be registered as valid transitions in
`schema.json`, enforced at startup by the existing schema validator.

Plugins receive a `ReadOnlyContext` — a sandboxed view of `PipelineContext`
that does not allow direct writes. This constraint ensures plugins cannot
corrupt pipeline state.

## Rationale
Plugins as a separate concern from executors keeps the core runtime clean.
Observability and extensibility become opt-in — implementors attach only what
they need without modifying executor code.

The event-based redirect mechanism for middleware plugins preserves graph
integrity. Plugins cannot redirect to arbitrary nodes — they can only emit
events that are already defined in the schema. This keeps the FSM fully
auditable and prevents plugins from silently corrupting flow.

`ReadOnlyContext` as the plugin interface ensures that side effects from plugins
are predictable. Plugins observe state, they do not modify it.

## Consequences

### Positive
- Observability concerns (logging, audit, metrics) are decoupled from executor logic
- Implementors can extend runtime behavior without touching core files
- Graph integrity is preserved — plugins cannot bypass schema-defined transitions
- Plugin behavior is declarative and visible in `plugins.json`

### Negative
- Additional complexity for contributors — plugin lifecycle and execution model
  must be understood before attaching plugins to nodes
- Middleware plugins add latency to the nodes they are attached to
- `on_false` events must be explicitly defined in `schema.json` — implementors
  must keep `plugins.json` and `schema.json` in sync
