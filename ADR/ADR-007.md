# ADR-007: PipelineContext Contract Clarity

## Status
#Accepted

## Date
2026-05-30

## Context
`PipelineContext` currently serves as the sole communication object between
all nodes in the pipeline. Its fields are implicitly divided into two categories:

**Native fields** — fields read and written by built-in executors
(`metadata`, `tools_data`, `background`, `response`, etc.). These have
implicit contracts: each native node knows which fields it reads and which
it populates. However, this contract is undocumented — contributors must
read executor source code to understand the communication pattern.

**Custom node communication** — covalve provides `add_handlers` and
`overrides` in `PipelineConfig` for implementors to inject custom nodes.
However, there is currently no designated space for custom nodes to
communicate with each other. Custom nodes that need to pass data between
themselves have two unacceptable options: polluting native fields with
unrelated data, or relying on implicit conventions that are not enforced.

A third concern is structural: `schema.json` is currently validated as a
plain `dict`. There is no typed model representing the schema structure,
making it harder to reason about, refactor, or extend the schema contract
in Python code.

## Decision

### 1. CoreSchema typed model
Introduce a typed model hierarchy to represent `schema.json` in Python:

```
Transition → StateConfig → CoreSchema
```

`Transition` represents a single transition entry (`to` field).
`StateConfig` represents a single state with its transitions map.
`CoreSchema` represents the full schema with `INITIAL`, `FINAL`, and `states`.

This replaces the current `dict` usage in `engine.py`, `init.py`, and
`pipeline.py`. Native nodes communicate via typed fields — the typed model
makes this contract explicit and statically checkable.

### 2. `local` field in PipelineContext
Add a single untyped field to `PipelineContext` for custom node communication:

```python
local: Optional[dict[str, Any]] = None
```

`local` is exclusively for custom-to-custom node communication. Native
executors never read or write this field. Implementors may store any
intermediate data here without risk of collision with native pipeline state.

Custom-to-native communication is intentional and documented: a custom node
that needs to feed data into a native node must populate the relevant native
field directly (`tools_data`, `background`, `metadata`, etc.). This is not
a workaround — it is the contract. The documentation will explicitly map
which native fields each native node reads, so implementors know exactly
where to write.

## Rationale
These two changes address the same underlying concern from different angles:
making the communication contract of `PipelineContext` explicit.

`CoreSchema` typed model makes the native contract statically verifiable.
`local` field gives custom nodes a designated, isolated space without
touching the native contract.

Keeping `local` untyped is intentional — covalve cannot anticipate every
implementor's data shape. ADR-005 compliance is maintained because custom
nodes must still return `model_copy(update={"local": ...})` rather than
mutating in place.

## Consequences

### Positive
- Native node communication contract becomes explicit and documented
- Custom nodes have a designated space — no more field pollution
- `CoreSchema` typed model enables static analysis and safer refactoring
- No breaking change to existing public API

### Negative
- `local` is untyped — no Pydantic validation for its contents, ADR-005
  compliance relies on convention rather than enforcement
- `CoreSchema` typed model requires migrating current `dict` usages in
  `engine.py`, `init.py`, and `pipeline.py`
- Implementors must still read documentation to understand which native
  fields to populate for custom-to-native communication
