# ADR-006: TERMINAL_RESPONSE as an Optional Core Node

## Status
#Proposed

## Date
2026-05-30

## Context
In the current pipeline, all execution paths eventually converge to `MAIN_LLM`
before proceeding to `SAVE_DATA_TO_PERSISTENCE`. This includes paths where the
response is already fully determined before `MAIN_LLM` is reached — most notably,
guardrail rejections where the rejection reason is already populated in
`PipelineContext.guardrail_rejection` by the time `GUARDRAIL` emits `OUT_OF_SCOPE`.

Routing a fully-determined response through `MAIN_LLM` wastes an LLM call on
content that requires no reasoning. For a guardrail rejection, the response is
deterministic — the implementor knows what to say without involving the LLM.
The same pattern applies to other future cases where a node can produce a
complete response without LLM inference.

The existing `INTERNAL_SERVER_ERROR` node is not a candidate for this pattern.
It carries a distinct identity as an error recovery node and should remain
separate.

## Decision
Introduce a `TERMINAL_RESPONSE` node as an optional core node. Its sole
responsibility is to forward `ctx.response` — already populated by the
preceding node — directly to `SAVE_DATA_TO_PERSISTENCE`, without invoking
any LLM.

The node itself contains no logic. The contract is:
**any node that transitions to `TERMINAL_RESPONSE` must populate
`ctx.response` before emitting the transition event.**

`TERMINAL_RESPONSE` is optional — its presence is declared in `schema.json`.
If absent, the pipeline behaves as before. When included, it provides a
zero-LLM-cost exit path for any node that can produce a complete response
on its own.

Example graph with `TERMINAL_RESPONSE`:
```
GUARDRAIL → TERMINAL_RESPONSE → SAVE_DATA_TO_PERSISTENCE
               ↑
   (any node that can produce a complete response)
```

Implementation is delegated to the implementor. covalve provides the node
and enforces the contract via documentation. The implementor decides what
`ctx.response` contains before transitioning to `TERMINAL_RESPONSE`.

## Rationale
Routing a pre-determined response through `MAIN_LLM` is a design smell —
it couples response delivery to LLM inference even when inference adds
no value. `TERMINAL_RESPONSE` makes the intent explicit in the schema:
this path does not need the LLM.

Schema-driven optionality is consistent with ADR-004 (GUARDRAIL as optional
node) and ADR-005 (no direct mutation). A node can be added or removed from
the graph without affecting other nodes, as long as the preceding node
populates `ctx.response` before transitioning.

## Consequences

### Positive
- Eliminates unnecessary LLM calls for deterministic responses
- Makes zero-LLM exit paths explicit and auditable in the schema
- Consistent with existing optional node pattern from ADR-004
- No changes required to core engine or existing executors

### Negative
- Implementors must remember to populate `ctx.response` before transitioning
  to `TERMINAL_RESPONSE` — failure to do so will result in an empty or null
  response reaching persistence
- Adds one more node concept for contributors to understand
